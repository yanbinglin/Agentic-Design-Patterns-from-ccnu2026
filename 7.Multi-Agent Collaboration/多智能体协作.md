## 二、从大模型到 Agent

### 1. 大模型能做什么

大模型具备以下能力：

- **理解与生成语言**：理解用户指令，回答问题，总结信息，生成文本和代码。
- **一定的推理能力**：分析问题、比较方案，并根据上下文推导答案。
- **根据上下文作答**：回答受到用户指令、对话历史和所提供资料的影响。
- **输出结果**：接收输入并生成回答，但通常不会自动持续执行现实任务或调用外部工具。

常见产品包括 ChatGPT、DeepSeek、豆包等。

### 2. 什么是 Agent

Agent 是一个围绕目标持续感知、计划、行动和调整的智能系统。

> **Agent = 大模型的理解与推理能力 + 目标驱动 + 工具使用 + 持续行动**

Agent 的基本过程：

1. **接收目标**：围绕特定目标开展工作，而不是只回答一个问题。
2. **感知环境**：获取并理解与任务相关的信息。
3. **制定计划**：根据任务要求安排执行步骤。
4. **执行行动**：调用搜索、代码执行、文件读写等工具。
5. **学习改进**：根据执行结果判断下一步，必要时修正方案，直到完成任务或达到停止条件。

## 三、单 Agent 与多 Agent

### 1. 以论文实验复现为例

**单 Agent**需要独立完成：

1. 阅读实验协议，明确数据和实验设置；
2. 运行基线模型，如 Transformer、GNN；
3. 保存 `.json`、`.pyth` 等结果文件；
4. 独立核验 Top-1 Accuracy、mAP 等指标。

**多 Agent**可以进行专业分工：

| 角色 | 主要职责 |
|---|---|
| 实验规划 Agent | 阅读协议，明确实验要求 |
| 实验执行 Agent | 运行模型，保存预测结果 |
| 结果整理 Agent | 整理预测文件和评价指标 |
| 独立审核 Agent | 重新计算指标，检查结果 |

多 Agent 的核心是：**共同目标、任务分解、专业分工、信息交接**。

### 2. 适用场景判断

选择单 Agent 或多 Agent，可以依次考虑：

1. **任务复杂程度**：单 Agent 能否独立完成？
2. **子任务独立性**：各项任务的边界是否清晰？
3. **交付结果可信度**：下游任务是否需要独立核验？
4. **收益与成本**：多次调用会增加时间和 token 消耗。

单 Agent 适合清晰、规模较小的任务；多 Agent 适合可以明确分工、并行处理并需要交叉验证的复杂任务。

### 3. 多 Agent 的价值与成本

**价值：**

- 专业化分工；
- 信息共享与交叉核验；
- 部分任务可以并行；
- 模块化、可扩展，并具有一定鲁棒性。

**成本：**

- Agent 之间需要通信；
- 增加调用、等待和协调成本；
- 中间交接可能出错；
- 长任务需要持续管理执行过程。

> 多 Agent 的价值来自有效的协作机制，而不是 Agent 数量越多越好。

### 4. 多 Agent 的基本组织条件

- **角色与责任**：谁负责规划、执行和审核？
- **通信通道**：Agent 之间如何传递信息？
- **任务流与协议**：何时交接、交付什么、如何验收？

## 四、上下文与通信方式

### 1. 共享上下文与隔离上下文

**共享上下文**：接班 Agent 可以查看前一角色的对话和工具记录。

- 优点：细节不容易丢失；
- 代价：历史越来越长，容易受到前人思路影响。

**隔离上下文**：每个 Agent 保留自己的工作记录，只交换结论、文件或消息。

- 优点：便于并行，职责边界清楚；
- 代价：必须设计规范的交接格式。

### 2. 两类底层通信思路

#### （1）消息传递 Message Passing

发送方 A 将数据显式打包并投递给接收方 B。

形式包括：

- 工具参数调用；
- 点对点消息；
- 发布/订阅消息总线。

同步调用时，A 阻塞等待 B 返回；异步调用时，A 发出消息后继续工作，B 从队列中处理。

适合轻量控制信令和任务派发，不适合直接搬运大体积明细。

#### （2）共享存储 Shared Storage

写入方 A 将结果写入公共位置，读取方 B 按路径读取。

形式包括：

- 共享结果文件；
- 产物路径或 URI；
- 共享进度表或黑板（Blackboard）。

优点是“零拷贝传址”和可追溯留存：只传文件路径，避免把大量数据塞入提示词。需要配合通知机制，并防止多个角色并发写入造成覆盖。

## 五、三种交接方式

### 1. 方式一：把下游 Agent 当作工具调用

适合短、字段固定、需要立即得到结果的交接。

```python
def writer_tool(*, topic: str, summary: str) -> str:
    return f"{topic}: {summary}"

result = writer_tool(
    topic="文本分类复现",
    summary="先核指标(Acc=0.833, F1=0.829)，再写报告",
)
```

同步调用过程：

1. 主控组装参数；
2. 调用 `writer_tool`；
3. 下游执行并生成结果；
4. 返回 `result`，上游继续执行。

设计接口时要明确：输入字段、返回值、超时时间、异常处理。不要把几千条预测明细直接放进参数中，以免上下文膨胀和内容错抄。

### 2. 方式二：长产物放入共享文件

体积大、需留存和反复核查的资料写入文件，交接时只传文件路径。

实验执行 Agent 生成：

- `output/metrics.json`：`Acc = 0.833`，`F1 = 0.829`；
- `output/predictions.json`：6 条真值与预测明细。

```python
# 上游写入
metrics_path.write_text(
    json.dumps(metrics, ensure_ascii=False, indent=2)
)

# 下游按路径读取
data = json.loads(
    artifact_path.read_text(encoding="utf-8")
)
```

并发写入的三种防错措施：

1. **按任务分文件**：文件名绑定 `task_id`，如 `metrics_repro01.json`；
2. **读写权限分离**：执行者写入，报告者和审核者只读；
3. **版本检查与合并审核**：记录时间戳和输入哈希，多方修改必须经审核节点合并。

### 3. 方式三：用消息总线异步协作

发布者只广播“发生了什么”，订阅者按主题异步响应。

示例主题：`experiment.completed`

- 管理者：更新任务状态；
- 报告撰写者：读取 `metrics.json` 并写报告；
- 独立审核者：读取 `predictions.json` 并复算指标。

```python
manager_inbox = bus.subscribe("experiment.completed")
writer_inbox = bus.subscribe("experiment.completed")
bus.publish("experiment.completed", envelope)
```

消息总线使发布者和接收者解耦。新增审核员或日志归档员时，不需要修改实验执行者代码。

### 4. 结构化消息信封

```json
{
  "sender": "runner",
  "target": "manager",
  "type": "result",
  "task_id": "repro-01",
  "payload": {
    "file": "output/metrics.json"
  }
}
```

接收方按四步处理：

1. 检查 `target`：是否发给自己；
2. 检查 `type`：任务、状态还是最终结果；
3. 使用 `task_id`：定位同一实验批次；
4. 读取 `payload`：按路径取得产物。

常用消息类型：`task_assigned`、`status_update`、`result`、`terminate`。

### 5. 交接方式选择表

| 交接内容 | 优先机制 | 特点 |
|---|---|---|
| 短、结构固定、马上要结果 | 工具参数 | 同步阻塞，字段契约清楚 |
| 长文档、数据表、需反复读取 | 共享文件 | 持久化留存，消息只传路径 |
| 多角色协同、异步状态通知 | 消息总线 | 一发多收，主题路由，需 ACK 与重试 |

推荐组合闭环：**先共享文件落盘 → 再由消息总线广播路径 → 下游按需调用工具读取并生成报告**。

## 六、六种协作方式

1. **顺序交接**：前一步产物是后一步必需输入。例：跑基线 → 写分析 → 出报告。
2. **并行处理**：互不依赖的任务同时进行。例：读协议与配置环境并行。
3. **辩论共识**：多角色正反交锋，减少开放性分析中的盲区。
4. **层级结构**：上层管理者拆解目标，下层专家执行具体任务。
5. **专家小组**：不同领域专家从互补维度评估同一对象。
6. **批评审阅**：生成者提交初稿，独立审核者依据证据核验放行。

### 流程选择原则

- 有产物依赖：使用**顺序**；
- 可以同时起步：使用**并行**；
- 发布前需要证据把关：使用**审阅**。

## 七、通信拓扑与控制权

### 1. 六种常见拓扑

- **单 Agent**：一个模型循环调用工具，适合简单任务；
- **网络/网状**：任意 Agent 可直接通信，灵活但路径难追踪；
- **监督者**：中心节点拆单、派发、汇总，控制清楚但可能成为瓶颈；
- **监督者作为工具**：把专家团队封装成主 Agent 的一个工具；
- **层级结构**：总管—组长—执行员，适合大型工程；
- **自定义图**：按业务依赖显式锁定有向边，如执行 → 分析 → 报告 → 审核。

对于实验复现，优先使用监督者或自定义图，以保证指标可溯源。

### 2. 三种控制模式

- **对等协作**：固定角色直接交接，链路短，但角色增多后规则容易膨胀；
- **管理者编排**：中心经理拆分、指派、监控和汇总，便于全局管理，但增加中心调用成本；
- **去中心化**：角色依据消息或共享状态自治响应，弹性高，但需防止循环触发或无人接单。

## 八、CrewAI 代码表达

### 1. 五个核心构件

| 构件 | 作用 |
|---|---|
| `Agent` | 谁参与 |
| `Task` | 交付什么 |
| `context` | 谁依赖谁 |
| `Process` | 怎样调度 |
| `kickoff` | 输入后启动 |

### 2. 基本代码骨架

```python
analyst = Agent(role="实验分析员", ...)
report_writer = Agent(role="复现报告撰写员", ...)

analysis_task = Task(agent=analyst, ...)
report_task = Task(
    agent=report_writer,
    context=[analysis_task]
)

crew = Crew(
    tasks=[analysis_task, report_task],
    process=Process.sequential
)
result = crew.kickoff(inputs={...})
```

同一个模型可以承担不同角色，真正的分工由 Agent 的目标和 Task 的约束决定。

### 3. 文件与实验主链路

1. `experiment_protocol.md`：定义任务、模型和指标；
2. `run_baseline.py`：运行朴素贝叶斯基线；
3. `predictions.json`、`metrics.json`：保存预测和指标；
4. `crewai_repro_report_demo.py`：分析员先解释，报告员后写报告；
5. `analysis.md`、`reproduction_report.md`：保存中间分析和最终报告；
6. 从逐条预测重算指标，与报告数字对照。

实验固定使用 12 条训练样本和 6 条测试样本，主要用于验证流程。

### 4. 两个角色的职责

```python
llm = LLM(
    model="gemini/gemini-3.6-flash",
    temperature=0.2
)

analyst = Agent(
    role="实验分析员",
    goal="只依据实验协议与指标文件说明配置、结果、证据路径和局限",
    llm=llm
)

report_writer = Agent(
    role="复现报告撰写员",
    goal="把实验分析写成初学者也能核对的中文复现报告，不杜撰指标",
    llm=llm
)
```

运行时顺序：获取基线指标 → 注入协议和指标 → 执行分析 Task → 报告 Task 接收分析 → 保存两个 Markdown 产物。

## 九、结果验证与排错

### 1. 三层可复查产物

1. **基线层**：指标和逐条预测已经保存；
2. **接力层**：分析稿先于报告生成；
3. **报告层**：报告包含证据路径和实验局限。

报告数字必须能够回查原始文件。

### 2. 误判案例

误判样本：`文档 · 清楚 · 训练 · 慢`。

测试准确率为 `0.833`。单 Agent 可能仅凭生成文本构造一个自洽解释，掩盖证据缺口；多 Agent 则回到 `predictions.json` 逐条溯源，用外部证据阻断主观合理化。

> 拒绝自我合理化，是工程防错的第一道防线。

### 3. 独立重算指标

混淆矩阵：

| 真实值 \\ 预测值 | 负类 | 正类 |
|---|---:|---:|
| 负类 | 3（TN） | 0（FP） |
| 正类 | 1（FN） | 2（TP） |

- 准确率：`5 / 6 = 0.833`；
- 负类：`TP=3, FP=1, FN=0`，`F1=0.857`；
- 正类：`TP=2, FP=0, FN=1`，`F1=0.800`；
- Macro-F1：`(0.857 + 0.800) / 2 = 0.829`。

**审计规则**：审核者必须基于外部证据独立重算；若数字不一致，就回滚并退回上游查日志。

### 4. 常见失效模式

| 缺口 | 表现 | 示例 |
|---|---|---|
| 设计缺陷 | 职责重叠、接口不清 | 两个 Agent 同时修改 `metrics.json`，导致覆盖 |
| 理解不齐 | 目标或信息被误解 | 把测试集准确率写成训练集结果 |
| 验收缺失 | 声称完成但未达标 | 未核对 `predictions.json` 就发布指标 |

Agent 之间传递的是会被重新理解的语义，因此必须定义边界，并保留可核查的原始证据。

## 十、控制流代码即护栏

Google ADK 可用以下构件固化任务关系：

- `SequentialAgent`：强制先后顺序；
- `ParallelAgent`：并行执行独立任务；
- `LoopAgent`：设置最大迭代次数，防止无限循环；
- `AgentTool`：把下游 Agent 封装为可调用工具。

> 代码不仅赋予 Agent 行动能力，也界定其行为边界。

隔离上下文中的交接应当包含：任务、产物、状态、验收标准和失败处理。例如：

```text
任务：解释文本分类基线实验
产物：metrics.json + predictions.json
状态：已完成；6 条中有 1 条预测错误
验收：从逐条预测重算准确率和 F1
失败：数值不一致则退回查日志
```

## 十二、总结

可信赖的多智能体系统有四个支柱：

1. **信息增量**：引入外部证据，击穿认知盲区；
2. **清晰分工**：角色职责和边界明确；
3. **可靠交接**：接口标准化，链路可追溯；
4. **独立验证**：确定性重算，保留审计痕迹。

> **好的多智能体系统 = 清晰分工 + 可靠交接 + 独立验证**
