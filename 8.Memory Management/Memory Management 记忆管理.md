## 1. 什么是智能体记忆

**智能体记忆（Agent Memory）**是保留并利用过去交互、观察和学习信息的能力。它帮助智能体维持对话上下文、做出更有依据的决策，并在后续任务中复用经验。

在课件讨论的调用方式下，LLM 每次只能看到本次请求提供的内容。用户上一轮说过的话，如果没有重新进入当前上下文，模型就无法据此回答。工程上的记忆管理，需要处理历史信息的保存、筛选、检索和上下文组装。

例如：

1. 第一轮用户说：“我叫 Sam，我下个月要去纽约。”
2. 第二轮用户问：“我的名字是什么？”
3. 第二轮请求没有历史时，模型答不出名字。
4. 将第一轮消息放入第二轮请求后，模型可以回答“Sam”。

### 为什么不能只扩大上下文窗口

- **容量有限**：更早的信息仍可能被挤出窗口。
- **缺少自动持久化**：窗口本身不负责跨会话保存信息，需要应用或外部服务存储并重新加载。
- **全量重放成本高**：每次发送全部历史会增加输入 token、费用和时延。
- **跨会话需求不同**：用户偏好、历史工单和任务经验需要独立于当前对话保存。

记忆设计的核心问题是：当前任务需要哪些信息，哪些信息值得长期保存，以及何时取回。

## 2. 短期记忆与长期记忆

### 2.1 短期记忆：当前工作的上下文

短期记忆（Short-Term / Contextual Memory）近似工作记忆，承载当前正在处理或刚接触的信息，例如：

- 最近的用户消息和智能体回复。
- 工具调用结果。
- 当前任务进度、中间结论和当轮反思。
- 较早对话的摘要。

这些内容进入模型上下文，直接影响下一步生成与行动。常见管理方法包括保留近期消息、摘要较早对话、突出关键事实，以及按相关性裁剪。

### 2.2 长期记忆：外部可检索的知识仓库

长期记忆（Long-Term / Persistent Memory）跨交互、跨任务或跨时间保存信息，常见载体包括：

| 载体 | 适合保存的内容或用途 |
| --- | --- |
| 数据库、文档库 | 结构化事实、用户画像、历史记录 |
| 知识图谱 | 实体及其关系 |
| 向量数据库 | 通过 embedding 支持语义相似度检索 |
| 托管记忆服务 | 将存储、处理和检索交给服务管理，如课件提到的 Memory Bank |

长期记忆的典型使用过程：查询外部存储，取回相关片段，将片段放入当前短期上下文，再与当前用户输入一起交给模型。

> 语义向量检索是长期记忆的一种实现方式。结构化事实也可以通过键值或数据库条件查询取回。

### 2.3 两类记忆的工程差异

| 维度 | 短期记忆 | 长期记忆 |
| --- | --- | --- |
| 作用域 | 单个会话或线程 | 跨会话，可绑定用户或其他命名空间 |
| 载体 | 当前上下文中的消息，以及会话状态 | 文件、数据库、向量库等外部存储 |
| 取用方式 | 选定消息直接进入 prompt | 按需读取或检索后注入 prompt |
| 主要问题 | 窗口溢出，历史增长导致成本上升 | 写入后未必能有效检索，还存在冲突和过期问题 |
| 应对方式 | 裁剪、摘要、按需注入 | 命名空间隔离、TTL、冲突消解、检索设计 |

**短期负责当前交互的连贯性，长期负责以后还能取回有用信息。**

## 3. 记忆读写的数据流

课件将写入和读取分成两条路径，在会话上下文中汇合。

### 写入路径

1. 用户消息、工具调用和环境观察形成事件（Event）。
2. 会话保存事件历史，并通过状态变更记录动态字段。
3. 在会话告一段落或需要记住某项信息时，将值得保留的内容写入长期记忆。

### 读取路径

1. 智能体根据当前问题检索相关历史知识。
2. 记忆服务返回相关片段。
3. 应用或框架把片段与近期消息组装成当前上下文。
4. 模型结合上下文推理并回答。

记忆作为外部组件参与 Agent 循环。跨进程使用时，实际存储必须独立于进程存活；仅存在 Agent 实例或内存对象中的数据无法满足这一要求。

## 4. 典型应用场景

| 场景 | 短期记忆的作用 | 长期记忆的作用 |
| --- | --- | --- |
| 聊天机器人、对话式 AI | 维持多轮对话和话题连续性 | 召回偏好、旧话题、历史工单 |
| 任务导向智能体 | 跟踪目标、步骤和当前进度 | 读取历史用户数据，复用任务经验 |
| 个性化体验 | 理解本次需求 | 保存画像、偏好和行为信息 |
| 学习与改进 | 记录当轮反馈与反思 | 保存成功策略、失败教训、新事实 |
| RAG 知识库问答 | 组织当前问题与检索片段 | 提供外部文档知识 |
| 自主系统 | 支持局部感知和即时决策 | 保存地图、路线及可复用规则 |

关联主题：第 14 章 Knowledge Retrieval（RAG，检索增强生成）。

## 5. Google ADK：Session、State 与 MemoryService

### 5.1 三个核心概念

| 概念 | 含义 | 主要内容 |
| --- | --- | --- |
| `Session` | 一条独立的对话线程 | 消息与动作的 `events`、动态字段 `state`，以及 `id`、`app_name`、`user_id`、更新时间等信息 |
| `State` | 会话中的键值草稿本 | 用户偏好、任务进度、中间结果和分支标记等可序列化数据 |
| `MemoryService` | 长期知识的写入与检索接口 | 历史会话或外部系统中的可检索内容 |

`events` 保存交互与动作历史，`state` 保存当前动态字段。State 的生命周期由键的作用域和存储后端共同决定。

课件将 Session 与 State 归入短期记忆层，将 MemoryService 归入长期记忆层。但这是一种职责划分：持久化的 Session 后端也能保存会话历史，`user:` 状态也能跨会话共享；它们与“按问题检索历史知识”的 MemoryService 用途不同。

### 5.2 SessionService 的后端选择

应用通常通过 `SessionService` 创建和读取 Session，而非直接构造会话对象。

| 实现 | 课件中的定位 | 持久性 |
| --- | --- | --- |
| `InMemorySessionService` | 本地开发、测试与调试 | 进程退出后丢失 |
| `DatabaseSessionService` | 自建生产环境，自己管理数据库 | 使用数据库保存会话 |
| `VertexAiSessionService` | Google Cloud Vertex 托管会话 | 由托管服务保存 |

### 5.3 一轮对话的处理流程

1. 用户发送消息。
2. Runner 通过 SessionService 获取或创建 Session。
3. Agent 读取 state 和历史 events，完成推理及工具调用。
4. Agent 产出回复，并可能产生状态变更。
5. Runner 调用 `append_event()` 追加事件，同时应用 `state_delta`。

由此形成两类数据：**可改写的状态字段**与**只追加的事件历史**。

### 5.4 State 键前缀与作用域

`session.state` 使用字符串键和可序列化值。课件介绍四类作用域：

| 前缀 | 作用域 | 生命周期 | 典型用途 |
| --- | --- | --- | --- |
| 无前缀 | 当前 Session | 随该会话存续 | 任务进度、会话标记 |
| `user:` | 同一应用中同一用户的多个会话 | 能否跨重启保留取决于后端 | 用户偏好、画像、长期设定 |
| `app:` | 应用全局，所有用户共享 | 能否跨重启保留取决于后端 | 全局配置、公共规则 |
| `temp:` | 单次调用 | 不持久保存 | 中间计算、一次性工具参数 |

示例：

```python
{
    "task_status": "active",
    "user:name": "Ada",
    "app:default_language": "zh-CN",
    "temp:step": 2,
}
```

### 5.5 正确写入 State

#### 方式一：output_key 保存智能体文本输出

在 `LlmAgent` 中声明 `output_key`，Runner 在处理输出事件时将文本写入对应状态键。

```python
agent = LlmAgent(
    name="greeter",
    model="gemini-2.0-flash",  # 课件中的模型名称
    instruction="记住用户的名字并问候",
    output_key="last_reply",
)
```

适合保存 Agent 的最终文本回复。课件第 13 页的实测还结合了工具对 `tool_context.state` 的修改，并完整执行 Runner 流程。最终状态包含 `last_reply`、登录次数及任务状态。应区分：文本输出由 `output_key` 保存，其他业务字段来自工具产生的状态变更。

#### 方式二：EventActions.state_delta 提交结构化变更

课件通过事件提交一次更新多个字段：

```python
await session_service.append_event(
    session=session,
    event=Event(
        author="system",
        actions=EventActions(
            state_delta={
                "task_status": "active",
                "user:login_count": 1,
            }
        ),
    ),
)
```

重新获取会话后，课件输出为：

```python
{"task_status": "active", "user:login_count": 1}
```

适用场景包括工具写状态、更新多个键、保存 JSON 或列表，以及更新用户级或应用级数据。工具内通过框架提供的 `ToolContext` 修改状态时，应让框架随事件提交变更。

#### 反例：直接修改取出的 Session 字典

课件第 15 页演示：

```python
session.state["task_status"] = "active"
# 随后重新通过 get_session() 获取会话
```

重新获取后，`task_status` 仍为 `idle`，`events` 数量为 0。该实验说明，直接修改拿到的会话对象，没有通过事件路径保存变更。

**应使用 Runner／工具上下文管理的状态更新，或显式提交 `EventActions.state_delta`。**

### 5.6 MemoryService 的两个核心接口

| 接口 | 功能 | 调用时机 |
| --- | --- | --- |
| `add_session_to_memory(session)` | 将会话内容交给记忆服务写入、处理或索引 | 会话告一段落，或用户明确要求记住信息时 |
| `search_memory(...)` | 搜索相关记忆片段 | 当前问题需要历史信息时 |

具体实现决定是否进行事实抽取、摘要或语义索引，不应仅凭接口名称假设这些能力都存在。

课件给出的实现选择：

- `InMemoryMemoryService`：测试用临时实现，进程退出后数据丢失。
- `VertexAiRagMemoryService`：课件中的生产方案，基于 Google Cloud RAG 提供持久存储及语义检索。

检索可以作为工具暴露给 LLM，由模型决定何时调用。课件跨会话示例使用了 `load_memory` 工具。

### 5.7 实验：跨会话检索与用户隔离

课件构造三个历史会话并写入记忆：

| 会话 | 用户 | 用户陈述 |
| --- | --- | --- |
| a | user1 | My favorite language is Python |
| b | user2 | I prefer Rust for systems work |
| c | user1 | I am learning Go this month |

检索调用的关键参数：

```python
result = await memory.search_memory(
    app_name=APP,
    user_id="user1",
    query="Python",
)
```

课件实测结果：

| 查询 | 用户 | 召回条数 |
| --- | --- | --- |
| Python | user1 | 2 |
| Python | user2 | 0 |
| Rust | user2 | 2 |

这里的 2 条包含用户陈述和对应模型回复，不能直接理解成两个独立事实。实验说明记忆按 `(app_name, user_id)` 隔离，同一用户可跨会话召回，另一用户无法检索到该用户的内容。

### 5.8 实验：全新会话中召回 Python 偏好

课件第 19 页展示：

1. 会话一中，用户说最喜欢的编程语言是 Python，随后将信息写入记忆。
2. 会话二使用新的 `session_id`，初始 `events=0`、`state={}`。
3. 用户问最喜欢哪种编程语言。
4. 模型调用 `load_memory`，查询 `favorite language`。
5. 工具命中历史陈述，模型回答 Python。

课件文字说明两次访问之间关闭并重新启动了程序。**这一结果以记忆存储确实跨进程保留为前提**，不能由 `InMemoryMemoryService` 单独实现。截图呈现了召回结果，但该页没有展示完整持久化实现。

## 6. LangChain：历史如何进入模型请求

### 6.1 不带历史：第二轮答不出名字

课件实验 1a 中，第一轮用户介绍姓名 Sam 和纽约旅行计划，第二轮单独询问姓名。

| 轮次 | 输入 token | 输出 token | 结果 |
| --- | --- | --- | --- |
| 第一轮 | 18 | 322 | 正常回应介绍 |
| 第二轮 | 12 | 39 | 无法回答姓名 |

第二轮输入没有携带第一轮内容。这些数字是课件特定实验的结果，不代表不同模型或运行环境的固定消耗。

### 6.2 手动拼接历史

课件实验 1 手动保存用户和助手消息，并在第二轮调用时加入历史。

- 模型成功回答 Sam。
- 第二轮输入为 354 token，输出为 77 token。
- 两轮后，历史容器中包含四条消息：用户、助手、用户、助手。

该实验说明历史注入能维持对话，也显示了全量重放带来的输入成本增长。

### 6.3 框架自动管理历史

课件实验 1b 使用 `RunnableWithMessageHistory`，让框架管理：读取历史、拼接 prompt、保存新消息。

第二轮无需业务代码手动拼接历史，模型仍回答 Sam，历史容器中有四条消息。自动管理改变了读写职责，模型仍依赖实际进入请求的上下文。

> 课件终端截图中，`InMemoryChatMessageHistory` 和 `RunnableWithMessageHistory` 出现弃用提示，其中后者提示使用 LangGraph 的内置持久化。这里保留它们用于解释课件实验，不将课件接口视为当前版本的实施建议。

### 6.4 文件存储与跨进程召回

课件实验 2 将内存存储替换为文件存储，验证过程为：

1. 在写入进程中保存历史信息。
2. 关闭进程。
3. 在新进程中从磁盘加载历史。
4. 询问姓名、饮食限制和下个月的目的地。
5. 模型回答：Sam、素食、纽约。

截图显示，新进程启动时从磁盘加载了 8 条历史消息，该次回答输入为 181 token、输出为 9 token。

**跨进程保留与检索方式是两个维度。** 该文件实验通过加载历史证明持久性，不等同于已经实现按语义检索长期事实。截图中“零历史注入”的表述，宜理解为业务调用未手工传入历史；框架加载的信息仍必须进入模型上下文，才能影响回答。

### 6.5 四个实验的递进关系

| 实验 | 历史处理方式 | 验证范围 | 结果与结论 |
| --- | --- | --- | --- |
| 1a 无记忆 | 第二轮不带历史 | 同一进程两轮 | 答不出 Sam，独立请求不自动继承上下文 |
| 1 手动历史 | 手工保存并拼接消息 | 同一进程两轮 | 答出 Sam，第二轮输入增至 354 token |
| 1b 框架管理 | 框架自动读写历史 | 同一进程两轮 | 答出 Sam，容器有四条消息 |
| 2 文件持久化 | 写入磁盘，新进程加载 | 跨进程 | 召回 Sam、素食、纽约 |

## 7. 长期记忆的三种内容类型

课件借用认知科学分类，说明不同信息需要不同更新和读取方式。

| 类型 | 记住什么 | 实现与使用方式 | 更新或风险 |
| --- | --- | --- | --- |
| 语义记忆（Semantic） | 事实，如用户身份、偏好、去过哪里 | 用户画像、可检索事实文档 | 同一事实字段更新或覆盖，避免旧值不断堆积 |
| 情景记忆（Episodic） | 经历，如过去如何完成任务 | 任务轨迹、成功步骤，作为 few-shot 示例复用 | 按相似任务召回，减少重复试错 |
| 程序性记忆（Procedural） | 行动规则、约束和操作方法 | 系统提示、指令集，也可通过反思提出修改 | 规则变化影响范围大，需要审核与护栏 |

事实适合精确读取和更新，经历适合相似度召回，规则修改需要控制影响范围。

## 8. 复习要点与工程边界

1. **历史必须进入当前请求才能发挥作用。** 存在某个数据库或文件里，不代表模型已经知道。
2. **短期记忆需要控制上下文成本。** 可结合近期消息、摘要和按需检索，避免无限重放历史。
3. **跨会话不等于跨进程。** 同一进程中的内存对象可以供多个会话复用，进程退出后是否保留由后端决定。
4. **State 的共享作用域不保证持久性。** `user:` 与 `app:` 表示共享范围，重启后的可用性还要看 SessionService。
5. **记忆服务的接口定位不保证实现能力。** 应分别核对持久化、事实抽取、检索及用户隔离。
6. **状态更新应走框架管理的事件路径。** 直接修改取出的 Session 对象可能无法保存。
7. **长期存储还需要维护。** 写入成功后仍需考虑能否检索、事实是否过期，以及新旧信息如何冲突消解。
8. **课件中的“学习与改进”主要体现为经验复用。** 保存失败教训或成功策略本身，不意味着更新模型参数。
